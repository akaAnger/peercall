# Optional TURN relay setup

PeerCall uses WebRTC. Browsers first try to connect peers directly; a public STUN server can help them discover usable network addresses, but STUN cannot relay media when a direct path is blocked.

A TURN server is the fallback for those restrictive cases. It relays encrypted WebRTC traffic between peers when firewalls, carrier-grade NAT, corporate networks, or symmetric NAT prevent a direct connection.

## Why PeerCall does not bundle TURN

PeerCall is intentionally a static, serverless project. Bundling a public TURN relay would add:

- an always-on server and bandwidth costs;
- credentials that must be protected and rotated;
- abuse and rate-limit concerns;
- an additional operator that can observe connection metadata.

For that reason, the default app remains direct-connection first and does not ship with relay credentials.

## Recommended configuration shape

If optional TURN support is added, keep relay configuration separate from the connection codes and avoid committing credentials to the repository.

A minimal `RTCPeerConnection` configuration can look like this:

```js
const rtcConfig = {
  iceServers: [
    { urls: "stun:stun.example.net:3478" },
    {
      urls: [
        "turn:turn.example.net:3478?transport=udp",
        "turns:turn.example.net:5349?transport=tcp"
      ],
      username: "temporary-user",
      credential: "temporary-password"
    }
  ]
};
```

Prefer short-lived TURN credentials generated by a service you control instead of hard-coded long-lived secrets. For a purely static deployment, users should provide relay settings locally at runtime rather than storing them in source files.

## Operational notes

- Support both UDP TURN and TLS/TCP TURN where possible; restrictive networks may block UDP.
- Test from two different networks, not only two devices on the same Wi-Fi.
- Monitor relay bandwidth and authentication failures because relayed audio can consume meaningful traffic over time.
- Treat TURN hostnames, usernames, and credentials as operational configuration rather than application defaults.
- Do not assume TURN improves privacy: media remains WebRTC-encrypted, but the relay operator can still observe metadata such as IP addresses, connection times, and traffic volume.

## Failure behavior

If direct ICE negotiation fails and no relay is configured, PeerCall should explain that the network may require TURN instead of presenting the failure as an unknown error. If a relay is configured but unreachable, the app should still fail clearly and allow the user to retry with direct connectivity or updated relay settings.

## Scope for a future implementation

A small implementation should:

1. accept optional TURN URLs and temporary credentials at runtime;
2. add them to the existing `iceServers` list;
3. never include TURN credentials in exported or shared connection codes unless explicitly required by the protocol design;
4. keep direct peer-to-peer connectivity as the preferred path;
5. document whether relay settings are stored locally and how users can clear them.

This keeps PeerCall's default deployment simple while making restrictive-network support possible for users who operate or trust a relay.
